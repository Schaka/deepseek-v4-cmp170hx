# Rebase to haosdent/vllm@12810046c — status

Branch: `rebase-12810046c`. **Not merged to `main`** — `main` stays on `c3046d1` until this
is fully validated with a real running server, not just static patch/compile checks.

## Why

haosdent's tip moved from `c3046d1` (2026-08-04) to `12810046c` (2026-08-05) as a single
"full campaign squash": 42 commits, 111 files, measured **2.42× TTFT@8K** (1089.9ms →
450.4ms), decode step ~12.1ms, gsm8k accuracy unchanged (0.97). It also backports six named
correctness fixes from `wtdcode/vllm-backport`, including the same `#49117` DSML
orphan-invoke recovery this repo's own `0009` ports.

Unlike `c3046d1`, `12810046c` is **normally git-reachable** (no force-push has orphaned it —
yet) — `launch/rebuild-image.sh` on this branch uses a plain shallow clone instead of the
tarball-recovery dance `main`'s version needs.

## ⚠️ A word on methodology, since it bit us here

The first pass at this triage tested each patch (`0010` through `0021`) as an **independent
dry-run against the pristine base**, not cumulatively. That's invalid for a sequential
patch series — several of these patches only make sense stacked on the ones before them
(`0012`-`0015` are explicitly "a six-patch hardening series... sequential and
interdependent" per this repo's own `patches/README.md`). That first pass reported
`0012`-`0015` as cascade-failing and `0005a` as producing duplicate definitions ("already
redundant"). **Both were wrong** — artifacts of testing in isolation (and, for `0005a`
specifically, an overlapping shell glob that applied it twice in the same test). Redone
properly (sequential, one patch at a time, checked for real), the picture is much better.
Lesson: always test a sequential series cumulatively, and watch for glob patterns that
match more than one file (`0005*` matches both `0005-` and `0005a-`).

## Remaining before this can merge to `main`

1. **A real build.** Static patch-apply + `py_compile` checks are necessary but not
   sufficient — none of this has actually compiled the C++/CUDA layers or run.
2. **Runtime verification of the `0006` conclusion** — push a served instance on this base to
   500k+ tokens and confirm no crash/OOM in the sparse-indexer path, since "the comment says
   M is bounded" is not the same as "verified under our actual PP4 + DSpark + fp8-KV config."
3. The full functional test suite `main`'s patches got (parser unit tests, the fuzzy-detector
   isolated tests, a real served-container smoke test, and ideally the same repetition-loop
   live-fire test `0021` got on `main`).
4. A decision on whether the measured 2.42× TTFT and the newer native SM80 kernels translate
   into a real decode/prefill win on the actual CMP 170HX hardware, not just haosdent's own
   benchmark rig — this repo's whole ethos is "measure on this hardware, don't trust claimed
   numbers" (see `RESULTS.md`'s own retraction of a circulated "+30%" claim for the `c3046d1`
   move). Don't merge on the strength of upstream's numbers alone.
